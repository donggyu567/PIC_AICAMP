# AI 분석 결과 입력 및 누적 계산 검증

이 문서는 현재 파일 기반 계산 API의 실행 안내다.

## 실행

프로젝트 최상위 폴더에서 실행한다.

```powershell
.\.venv\Scripts\Activate.ps1
python -m uvicorn backend.main:app --reload
```

http://127.0.0.1:8000/docs 에서 `POST /api/v1/dev/model-results`를 선택한다.
Swagger의 기본 Example Value는 바로 실행할 수 있는 샘플이다.
이 경로는 LLM·AI를 호출하지 않으므로 API 키나 모델 파일이 필요하지 않다.

## 순차 확인

1. 기본 샘플을 실행하면 현재 점수 55, 누적 점수 약 55가 반환된다.
2. 같은 통화 ID에서 `utterance_id`와 `sequence`를 모두 2로 바꾸고 실행한다.
3. 현재 점수 55, 누적 점수 약 73.75가 반환된다.
4. 같은 요청을 다시 보내면 409가 반환된다. 새 테스트는 다른 통화 ID와 순서 1로 시작한다.

입력 점수는 0~1, 응답의 현재·누적·유형별 점수는 0~100이다.
반환 점수는 반올림하지 않는다. `calculation`에는 최대 점수, 누적식 점수,
실제 계산 창의 발화 ID 및 설정을 담는다.
현재 `window_size=20`, `rho=0.95`, `b=0.1`은 개발 설정이며 검증 완료된 운영 기준이 아니다.
통화가 처음 생성될 때 설정을 함께 저장한다. 코드의 기본값을 변경해도 이미 저장된
통화는 기존 설정으로 계산하고, 새로운 통화부터 변경된 기본값을 사용한다.

## 저장과 복원

저장 위치는 프로젝트 내 `backend/data/analysis/<통화 ID의 SHA-256 해시>.json`이다.
실행 위치와 무관하게 같은 프로젝트 경로를 사용한다. 실제 요청을 처리할 때 폴더를 생성한다.
`backend/data/`는 기존 `.gitignore`에 포함되어 있다.

통화별 파일에는 다음 내용을 함께 담는다.

- `storage_version`: 파일 형식 버전
- `conversation_id`: 통화 ID
- `policy`: 해당 통화의 계산 설정
- `records`: 발생 순서대로 저장한 발화 기록
  - `model_result`: 0~1 단위의 AI 분석 입력
  - `response`: 실제 반환한 0~100 단위의 계산 응답 JSON
  - `previous_attempts`: 재시도 이전의 실패 입력·응답을 발생 순서대로 보존한 목록

이 파일은 서버 복원을 위한 저장 형식이다. 외부 응답에 해당하는 JSON은 각 기록의
`response`이며, 조회 API는 이 부분만 반환한다. 경고 구현체가 연결되면 `warning`과
`evidence`도 포함하고, 미연결이면 두 필드는 `null`이다.
연결된 통화는 `warning_config`, `warning_state`, `pending_notification_ids`도 같은 파일에 저장한다.

처리 순서는 파일 읽기 → 중복·순서·이전 실패 확인 → 계산 → 응답 생성 → 파일 저장 → 반환이다.
기존 메모리 `AnalysisStore`는 읽어 온 발화의 중복·순서를 검사하는 데 계속 사용한다.
임시 파일에 UTF-8 JSON을 쓰고 flush/fsync를 수행한 뒤 같은 폴더에서 `os.replace`로 교체한다.
통화 전체 이력을 파일 하나로 교체하므로 입력만 저장되고 응답은 누락되는 상태를 줄인다.
여러 worker/프로세스에서의 동시 쓰기는 지원하지 않는다. 현재 서버는 단일 worker로 실행한다.

계산 API는 매 요청마다 파일에서 이력을 읽으므로 서버 재시작/자동 reload 후에도 이어서
계산할 수 있다. 이 기능은 개발용 계산 경로에 해당하며, 기존 발화 보정·문맥 경로의
메모리 상태까지 복원하지는 않는다. 이 기능 추가 전에 메모리에만 있던 기록은 자동 이전되지 않는다.

## 저장 결과 조회

`GET /api/v1/dev/model-results`에서 다음 쿼리를 사용한다.

- `conversation_id` 필수: 해당 통화의 최신 응답 반환
- `utterance_id` 선택: 해당 발화의 응답 반환

예시:

```text
/api/v1/dev/model-results?conversation_id=api-test-001
/api/v1/dev/model-results?conversation_id=api-test-001&utterance_id=1
```

AI 호출이나 재계산 없이 저장된 응답을 반환한다. 해당 통화/발화가 없으면 404다.
최신 발화가 분석 실패였다면 최신 조회도 그 실패 응답을 반환한다.
복구 후에는 같은 발화를 조회해도 복구된 현재 응답을 반환한다.
이전 실패 응답은 파일의 `previous_attempts`에 보존하며 현재 조회 API에는 포함하지 않는다.
응답을 받지 못해 같은 POST를 재전송한 경우 이미 저장되었다면 409가 나오며,
발화 ID를 지정해 조회하면 앞서 저장된 응답을 확인할 수 있다.

복원 확인: 첫 발화 저장 → 서버 재시작 → GET으로 첫 응답 확인 → 두 번째 발화 POST.
둘 다 55점인 기존 예제에서는 재시작 후에도 두 번째 누적 점수가 약 73.75다.

## 실패 발화 복구

`POST /api/v1/dev/model-results/retry`로 같은 발화를 재분석한 결과를 등록한다.
AI를 자동 호출하거나 자동 재시도하는 기능은 아니다. 입력 JSON 형식은 신규 결과 POST와 같다.

재시도 조건:

- 통화의 마지막 발화가 현재 `analysis_status="error"`여야 한다.
- `conversation_id`, `utterance_id`, `sequence`, `revision`, `tuned_text`가 실패 기록과 같아야 한다.
- 현재 신규·재시도 경로 모두 `revision=1`을 사용한다. 재시도 횟수만큼 revision을 올리지 않는다.
- `model_version`에는 재분석에 실제 사용한 버전을 보낸다. 이전 시도의 버전도 이력에 남는다.
- 성공한 발화를 다시 수정하거나 문장을 변경하는 정정 처리는 아직 지원하지 않는다.

처리 순서: 실패 대상 확인 → 이전 성공 발화들과 재시도 결과로 계산 → 이전 실패를 이력으로
보존 → 현재 결과 교체 및 파일 저장 → 응답 반환. 실패 발화를 새 발화로 추가하지 않으므로
발화 수와 발생 순서는 그대로 유지된다. 통화에 저장된 원래 계산 정책을 사용한다.

재분석도 실패했다면 세 점수·유형 필드를 `null`로 보내 실패 시도를 기록할 수 있다.
이 경우 응답은 HTTP 200 / `analysis_status="error"`이며 후속 발화 차단은 유지된다.
복구 성공 시에는 다음 발화를 신규 결과 POST로 보낼 수 있다. 앞서 차단된 요청은
저장·대기열에 보관되지 않으므로 호출자가 다시 전송해야 한다.

Swagger 확인 순서:

1. 새로운 통화 ID로 신규 결과 POST에 1번 발화 0.55를 전송한다.
2. 같은 통화의 2번 발화는 `analysis_status="error"`, 세 점수·유형 필드는 모두 `null`로 전송한다.
3. 3번 발화를 신규 결과 POST로 보내면 409로 차단된다.
4. 재시도 POST에 2번 발화의 원래 식별 정보·문장을 유지하고 성공 결과 0.55를 보낸다.
5. 두 번째 누적 점수 약 73.75가 반환된다. 이제 3번 발화를 다시 보내면 접수된다.

재시도할 통화가 없으면 404, 실패 대상 불일치 또는 이미 성공한 대상이면 409다.
입력 계약 오류는 422, 저장 실패는 503이다. 저장 실패 시 원래 실패 기록과 이력이 그대로
유지되므로 다시 시도할 수 있다. 성공 응답을 받지 못하고 같은 결과를 재전송해 409가 나오면
기존 GET API로 해당 발화의 현재 응답을 확인한다.

이전 파일에 `previous_attempts`가 없어도 빈 목록으로 읽는다. 이후 복구·저장부터
이력 필드가 포함된다. 저장 파일을 삭제하거나 초기화할 필요는 없다.

## 실패와 충돌

- 분석 실패 입력: `analysis_status="error"`로 두고 `is_phishing_score`,
  `type_scores`, `detected_types`를 모두 `null`로 설정한다.
- 유효한 실패 결과는 저장하고 HTTP 200을 반환한다. 응답 점수·유형·계산 결과는 `null`이다.
- 이전 분석 실패가 있으면 후속 발화는 409로 차단한다. 실패는 retry 경로로 복구할 수 있으며,
  문장 정정과 그에 따른 후속 발화 재처리는 아직 미구현이다.
- 중복 ID 또는 잘못된 발생 순서는 409, 입력 필드·점수 범위·성공/실패 계약 오류는 422다.
- 파일 읽기·쓰기 또는 저장 형식 검증 실패는 503이다. 손상된 파일을 빈 통화로 취급하거나
  자동으로 덮어쓰지 않는다. 임시 파일 작성/교체가 실패하면 기존 정상 파일을 유지한다.
- 분석 실패 기록도 재시작 후 유지되므로 서버를 재시작해도 후속 발화 차단은 풀리지 않는다.
  재시도 결과가 성공으로 저장되어야 차단이 풀린다.

## 현재 범위

- 이 API는 서버 계산 검증용이다. 앱에서 전달한 점수를 실제 AI 판정으로 사용하는 운영 경로가 아니다.
- 기존 `/api/v1/utterances`는 보정·문맥 확인 경로다. 새 `/api/v1/utterances/analyze`는
  보정부터 AI 호출·계산·저장까지 연결하며, 실제 AI 구현체 등록은 아직 필요하다.
  자세한 계약은 [통합 분석 안내](INTEGRATED_ANALYSIS_API.md)를 참고한다.
- 경고 호출·상태 저장 연결부는 준비되어 있다. 현재 실제 경고 구현체가 없으므로
  `warning`·`evidence`는 `null`이다. [경고 연동 안내](WARNING_INTEGRATION.md)를 참고한다.
- 분석 입력·계산 응답·정책을 JSON 파일에 보관하며 GET으로 다시 조회할 수 있다.
- 현재는 통화 전체 파일을 매번 읽고 교체하는 개발 구조다. 다중 프로세스 처리는 DB 등 별도 저장소가 필요하다.
- 통화 종료 상태 저장·후속 분석 차단은 구현되어 있다. DB 저장, 실제 AI·경고 구현체 등록,
  경고 모듈의 종료 이벤트 처리, 실제 알림 전송은 후속 단계다.

## 이번 단계 코드 역할

- `backend/stores/analysis_file_store.py`: 현재 결과·이전 시도 형식 검증, 파일 읽기, 원자적 파일 교체
- `backend/services/analysis_response.py`: 내부 점수를 응답 단위로 변환하고 응답 객체 생성
- `backend/services/analysis_service.py`: 저장 이력 복원, 계산, 실패 복구, 저장 및 조회 흐름 관리
- `backend/main.py`: 신규 POST·재시도 POST·GET 연결, 409/404/503 응답 처리

`process_model_result()`는 이제 `ModelResultRequest`를 받아 저장 완료된
`CalculationPreviewResponse`를 반환한다. 실패 분석도 `None` 자체를 반환하는 대신
점수와 `calculation`이 `null`인 응답 객체를 반환한다. 순수 계산 함수 `calculate_risk()`의
입력·출력은 기존과 같다.

## 자동 검증

```powershell
python -B -m unittest discover -s tests -p test_analysis_api.py -v
```

외부 API 호출 없이 순차 누적, 통화 분리, 최근 20개 제한, 중복·순서 충돌,
실패 차단, 입력 검증과 Swagger 샘플을 확인한다. 추가로 새 저장소 객체를 이용한 복원,
정책 유지, 최신/특정 발화 조회, 파일 교체 실패 후 재시도, 손상된 파일 보호,
통화 ID 경로 처리, 동시 중복 요청도 검증한다. 복구 성공·재실패·잘못된 재시도 대상,
재시작 후 복구, 복구 저장 실패, 동시 복구 요청, 기존 파일 호환 및 이력 검증도 포함한다.
테스트 데이터는 임시 폴더에만 기록한다.
기존 `test_backend_api.py` 및 `test_backend_pipeline.py`는 삭제된 이전 백엔드 구조를
대상으로 하므로 이번 테스트와 별도로 현 구조에 맞게 정리해야 한다.

## 통화 종료

`POST /api/v1/conversations/end`에 아래 JSON을 전달한다.

```json
{"conversation_id": "api-test-001"}
```

성공 응답은 `conversation_id`, `conversation_status: "ended"`, 서버 UTC 시각인
`ended_at`을 포함한다. 종료 상태를 파일에 저장한 뒤 200을 반환한다.

- 반복 종료는 저장을 반복하지 않고 최초 종료 시각을 반환한다.
- 저장된 분석 기록이 없는 통화는 404다. 보정 전용 API만 사용한 통화도 포함한다.
- 입력 형식 오류는 422, 파일 읽기·쓰기 실패는 503이다. 저장 실패 시 기존 파일을 보존한다.
- 실패 분석이 남아 있어도 종료할 수 있다. 실패 점수의 null과 이전 시도 이력은 유지한다.
  종료 후 재시도는 불가능하므로 복구가 필요하면 종료 전에 수행한다.
- 종료 후 신규 결과 등록·재시도·통합 분석·기존 보정 요청은 409로 차단한다.
  통합 분석 API는 AI 미등록 시 의존성 검사에서 먼저 503을 반환할 수 있다.
- 기존 GET으로 최신/특정 발화 응답을 계속 조회할 수 있다. 종료가 마지막 분석 응답을 바꾸지는 않는다.
- 경고 상태·근거·알림 대기 목록을 보존하며 종료 시 AI나 경고 모듈을 호출하지 않는다.
  `conversation_ended=True`를 통한 경고 이벤트 종료는 실제 모듈 합병 후 연동 범위다.
- 종료와 분석은 같은 프로세스의 잠금을 사용한다. 분석이 먼저 잠금을 잡았다면 분석 저장 후
  종료하며, 종료가 먼저라면 이후 분석을 차단한다. 현재는 단일 worker 전용이다.

주요 구현은 `analysis_service.end_conversation()`과 `ensure_conversation_active()`다.
신규·재시도 경로는 잠금과 종료 검사를 마친 후 내부 `_process_model_result_locked()` 또는
`_retry_model_result_locked()`를 사용하므로 통합 경로에서 통화 파일을 다시 읽지 않는다.

종료 테스트를 포함한 관련 검증 명령:

```powershell
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -p "*analysis_api.py" -q
```
