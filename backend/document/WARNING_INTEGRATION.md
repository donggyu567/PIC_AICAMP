# 경고 모듈 서버 연결

## 현재 범위

서버는 계산 결과와 직전 경고 상태를 `WarningManager.update_warning()`에 전달하고,
반환된 경고·근거·상태·알림 요청 ID를 저장할 수 있다. 실제 정책 판단·근거 관리·문구 생성은
팀원의 경고 구현체가 담당한다. `models/warning_manager`의 내부 로직은 이번 단계에서 구현하지 않았다.

현재 실제 구현체는 등록되어 있지 않다. 테스트용 구현체로 연결 계약만 검증했다.

## 구현체 등록과 통화 설정

서버 시작 시 팀원이 제공한 실제 구현체를 `app.state.warning_manager`에 등록한다.
이 객체에는 공통 계약의 `update_warning()` 메서드가 있어야 한다.

- 미등록 상태에서 시작한 통화: 계산·저장을 수행하되 응답의 `warning`, `evidence`는 `null`이다.
- 등록 상태에서 시작한 통화: 매 발화마다 경고 모듈을 호출하고 결과·상태를 함께 저장한다.
- 이미 경고를 관리하던 통화에서 구현체가 빠지면 503으로 처리한다.
- 경고 없이 시작한 통화에 중간부터 구현체를 붙이면 409다. 새로운 통화 ID로 시작한다.
  과거 이력을 재생해 경고를 소급 구성하는 마이그레이션은 아직 구현하지 않았다.

미연결의 `null`과 연결된 모듈이 판단한 `warning.status="none"`은 의미가 다르다.
클라이언트는 `null`을 안전 판정으로 해석하면 안 된다.

첫 호출 시 `WarningConfig()`의 개발 기본값(개별 근거 50점, 경고 70점)을 통화에 저장한다.
후속 처리와 실패 복구에서는 파일의 동일 설정을 사용한다. 검증이 완료된 운영 기준은 아니다.

## 서버 처리 순서

```text
AI 결과 검증
 → 누적 계산
 → 저장된 이전 경고 상태·설정 준비
 → 경고 모듈 호출
 → 반환 계약 검증
 → 점수 + warning + evidence 응답 조립
 → 분석 기록·응답·경고 상태·알림 대기 ID 함께 파일 저장
 → 응답 반환
```

경고 호출 입력:

- `model_result`: 현재 발화 분석 결과
- `calculation_result`: 성공 시 계산 결과, AI 실패 시 `None`
- `previous_state`: 직전 저장 상태, 최초에는 `None`
- `config`: 통화에 저장한 경고 설정
- `is_replay=False`, `conversation_ended=False`

현재 실패 복구는 아직 성공하지 않은 마지막 발화를 재분석하는 흐름이므로 실시간 호출이다.
문장 정정에 따른 과거 발화 재생과 통화 종료 호출은 이번 단계에 포함되지 않는다.

## 반환값 처리

| 경고 모듈 반환값 | 서버 처리 |
|---|---|
| `result.warning` | API 응답에 포함 |
| `result.evidence` | API 응답에 포함 |
| `state` | 통화 파일의 `warning_state`에 저장, 다음 호출 시 전달 |
| `notify_event_id` | 값이 있으면 `pending_notification_ids`에 중복 없이 추가 |

새 서버 저장 필드:

- `warning_config`: 통화별 경고 설정
- `warning_state`: 직전 경고 상태 및 근거·이벤트 이력
- `pending_notification_ids`: 아직 전송기를 연결하지 않은 알림 대기 ID

이 세 필드는 외부 API 응답에 포함하지 않는다. 기존 점수·응답과 같은 JSON 파일에 기록하며
파일 교체가 실패하면 이전 파일을 유지한다. 경고 모듈도 DB 저장이나 알림 전송 같은 외부
부수효과 없이 반환값을 만드는 계약을 지켜야 한다.

알림 ID는 저장만 한다. 실제 앱 알림 전송, 발송 완료 처리와 전송 재시도는 아직 없다.
이번 중복 방지는 대기 목록에 같은 ID를 중복 추가하지 않는 범위다.

## 반환 검증과 실패

서버는 `WarningUpdate`의 중첩 타입, 상태의 통화·설정, 응답과 상태의 일치, 점수 단위,
알림 이벤트 존재 여부 등을 확인한다. 정책 임계값으로 경고 상태를 다시 판단하지 않는다.
이전 상태와 입력은 깊은 복사본을 넘겨 구현체가 수정해도 기존 서버 기록을 보호한다.

AI 분석 실패 시:

- 현재 점수·누적 점수·현재 유형 필드는 `null`이다.
- 경고 모듈에 `calculation_result=None`을 전달한다.
- 기존 경고 상태와 근거는 유지해야 한다. 첫 실패 상태는 `None`이다.
- 알림 ID를 반환할 수 없다.
- 실패 안내 문구는 경고 모듈이 반환한 내용을 사용한다.

경고 모듈 예외·잘못된 반환값은 503이다. 해당 발화의 점수·상태를 부분 저장하지 않는다.
파일 저장 전 실패이므로 같은 발화를 다시 처리할 수 있다. 통합 분석 경로에서는 재요청 시
보정·AI도 다시 호출될 수 있다. 오류 로그는 예외 클래스명만 기록한다.

## 적용 경로와 테스트

신규 및 실패 재시도에 모두 연결했다.

- `/api/v1/dev/model-results`
- `/api/v1/dev/model-results/retry`
- `/api/v1/utterances/analyze`
- `/api/v1/utterances/analyze/retry`

GET 결과 조회는 저장된 `warning`·`evidence`도 그대로 반환하며, 모듈을 다시 호출하지 않는다.

```powershell
python -B -m unittest discover -s tests -p '*analysis_api.py' -v
```

테스트용 경고 구현체로 상태 직렬화·복원·다음 호출 전달, 첫 AI 실패, 기존 상태 유지,
복구 연동, 경고 예외·잘못된 상태 차단, 파일 쓰기 실패, 알림 ID 중복 방지를 검증한다.
실제 경고 정책의 판단 정확도와 실제 알림 전송은 검증하지 않았다.
