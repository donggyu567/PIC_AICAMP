# 발화 보정부터 위험도 계산까지 통합 연결

## 현재 연결 범위

`POST /api/v1/utterances/analyze`는 마스킹 발화 → LLM 보정 → AI 문맥 구성 →
등록된 AI 호출 → 결과 검증 → 누적 계산 → JSON 파일 저장을 연결한다.

실제 위험 탐지 모델은 아직 이 저장소에 없다. 기본 실행 상태에는 AI 구현체가
등록되어 있지 않으므로 새 통합 API는 보정 호출 전에 503을 반환한다.
임의 점수를 반환하는 기본 AI는 제공하지 않는다. 통합 테스트에서만 대체 AI를 사용한다.

기존 `/api/v1/utterances`는 보정·문맥 확인 경로로 유지한다.
`/api/v1/dev/model-results`는 분석 결과를 직접 넣어 계산하는 개발 경로로 유지한다.
앱 네트워크 코드는 이번 단계에서 변경하지 않았다.

## 요청과 응답

통합 분석의 요청은 기존 앱 입력과 같은 여섯 필드다.

```json
{
  "schema_version": "1.0",
  "conversation_id": "integrated-test-001",
  "utterance_id": 1,
  "masked_text": "안녕하세요",
  "has_masked_data": false,
  "masked_types": []
}
```

같은 통화에서 `utterance_id`는 1부터 연속으로 전달한다. 서버가 `sequence`를 부여한다.
응답은 `CalculationPreviewResponse`로, 점수 단위는 0~100이다. 경고 구현체를 등록하면
`warning`·`evidence`를 포함하고 미연결이면 두 필드는 `null`이다.
개발용 결과 입력 경로와 통합 경로는 같은 계산 저장소를 사용하므로 테스트 목적별로
서로 다른 통화 ID를 권장한다. 기존 보정 확인 경로의 메모리 기록은 통합 저장소로 자동 이전되지 않는다.

## 정상 처리 순서

1. 마스킹 입력 계약을 검증한다.
2. 파일에서 통화 이력을 읽고 이전 실패·발화 중복·순서를 확인한다.
3. 기존 `CorrectionEngine`으로 현재 발화를 보정하고 `merge_utterance()`로 병합·검증한다.
4. 저장된 이력에서 이전 최대 5개 `tuned_text`를 오래된 순서대로 꺼낸다.
5. 현재 보정 문장과 이전 문장 목록으로 AI 구현체를 호출한다.
6. AI 점수의 범위·8개 유형·중복 감지 유형 등을 검사한다.
7. 기존 계산 서비스로 최근 20개 누적 계산을 수행하고, 등록된 경고 구현체가 있으면
   이전 상태와 함께 호출한다. 분석 결과·응답·갱신된 경고 상태를 함께 저장한다.
8. 저장이 완료된 계산 응답을 반환한다.

AI 문맥은 별도 메모리 버퍼에 추가하지 않고 저장된 보정 문장으로 구성한다.
따라서 통합 경로는 서버를 재시작한 뒤에도 이전 문맥을 이어서 사용할 수 있다.
기존 보정 확인 경로의 `ConversationContextManager` 메모리는 이와 별개다.

현재는 공통 `RLock` 안에서 검증·외부 호출·계산·저장을 처리한다. 같은 스레드가
통합 처리에서 계산 서비스로 들어가도 잠금을 다시 잡을 수 있으며, 중복 요청의
불필요한 AI 호출을 막는다. 단일 worker용 개발 구조로, 서로 다른 통화의 외부 호출도
순차 처리된다. 통화별 병렬 처리와 처리량 개선은 이후 단계다.

## AI 담당자 연결 계약

`backend/services/ai_service.py`에 `RiskAnalyzer` 인터페이스를 정의했다.

- `model_version`: 비어 있지 않은 모델 버전 문자열, 최대 120자
- `analyze(model_input: RiskModelInput) -> RiskModelScores`

`RiskModelInput`:

- `current_text`: 현재 보정 문장
- `history_texts`: 이전 최대 5개 보정 문장 tuple, 오래된 것부터

`RiskModelScores`:

- `is_phishing_score`: 0~1
- `type_scores`: 계약에 정한 8개 유형 전체, 각각 0~1
- `detected_types`: 감지 유형 list, 없으면 빈 목록

구현체는 모델 점수와 유형 판정을 위 객체로 변환해 반환한다. 실패 시 예외를 발생시킨다.
서버는 유형 임계값을 임의로 적용하거나 과거 유형을 현재 결과로 복사하지 않는다.
토큰화, 모델의 입력 길이 제한, sigmoid 적용 여부와 출력 단위 변환은 실제 AI 어댑터에서
확인해야 한다. 아직 실제 모델·tokenizer를 받아 검증하지 않았다.

서버 시작 시 로딩한 구현체를 `app.state.risk_analyzer`에 등록하면 새 경로가 사용한다.
현재는 실제 구현체 로더가 없으므로 이 등록 작업은 미완료다.
`get_risk_analyzer()`는 등록 여부·호출 함수·모델 버전을 확인한다.

## 실패와 재시도

| 상황 | 처리 |
|---|---|
| AI 구현체 미등록 | 503, LLM 보정도 호출하지 않음 |
| 마스킹 계약 오류 | 422, 모델 호출·저장 없음 |
| 중복·순서·이전 실패 충돌 | 409, 모델 호출·저장 없음 |
| 보정 실패 | 502, 순서 진행·분석 결과 저장 없음 |
| AI 추론 실패 또는 잘못된 출력 | 실패 기록 저장, HTTP 200 / analysis_status=error / 점수 null |
| 저장소 읽기·쓰기 실패 | 503, 기존 파일 유지 |
| 경고 모듈 호출·반환 계약 오류 | 503, 해당 발화 부분 저장 없음 |

AI 호출 오류 로그에는 예외 클래스명만 남기고 원문 메시지·발화 문장을 남기지 않는다.
AI 추론 실패는 0점으로 대체하지 않는다.

`POST /api/v1/utterances/analyze/retry` 요청:

```json
{
  "conversation_id": "integrated-test-001",
  "utterance_id": 1
}
```

저장된 마지막 실패 발화와 이전 문맥으로 AI만 재호출한다. 보정 문장은 이미 저장돼 있으므로
LLM을 다시 호출하지 않는다. 기존 복구 서비스를 통해 과거 실패 시도를 보존하고,
성공 시 후속 차단을 해제한다. 후속 발화는 호출자가 다시 전송해야 한다.

이 경로와 개발용 `/api/v1/dev/model-results/retry`는 역할이 다르다.
통합 경로는 등록된 AI를 호출하고, 개발용 경로는 재분석 점수를 직접 받는다.
파일 저장 전에 실패한 신규 요청을 다시 보내면 보정·AI가 다시 호출될 수 있다.
완료된 결과 조회는 기존 GET `/api/v1/dev/model-results`를 사용한다.

경고 연동의 입력·반환·상태 보존 규칙은 [경고 연동 안내](WARNING_INTEGRATION.md)를 참고한다.
현재 실제 AI 구현체와 경고 구현체는 모두 별도 등록이 필요하다.

## 자동 검증

```powershell
python -B -m unittest discover -s tests -p '*analysis_api.py' -v
```

기존 계산 API와 통합 분석 API를 함께 검사한다. 임시 저장 폴더와 대체 제공자만 사용하며
실제 OpenAI API나 위험 탐지 모델은 호출하지 않는다. 보정은 기존 `CorrectionEngine`에
테스트용 LLM 제공자를 연결해 검증한다.
