# PIC Server v2

새 파이프라인을 구현할 FastAPI 서버다. 프로젝트 목표는 [루트 README](../README.md)를 따르고, **새 서버의 구현 순서·현재 위치는 이 문서에서 관리한다.** 기존 서버의 기능은 [backend 문서](../backend/document/README.md)를 참고하되, 새 서버에 이미 연결된 것으로 간주하지 않는다.

## 현재 위치

최종 갱신: 2026-11-06

- **완료:** 0단계 최소 서버. FastAPI 실행 진입점과 `GET /health` 구현.
- **현재 위치:** 6단계의 서버 측 결과 조회·알림 조회/수신확인·통화 종료 API 연결과 관련 검증을 마쳤다. 종료 요청의 마지막 발화 번호를 확인하고 마지막 분석 결과를 함께 반환한다. 동의 철회·삭제와 앱 연결은 아직 남아 있다. 보정·문맥 판단을 AI 실행 전 OpenAI 한 번의 호출로 통합했다. 실제 호출 2건과 임시 AI 분석·저장 조회를 확인했다. 판단 품질은 미검증이다.
- **앱 진행:** 실기기에서 STT 발화 수, 마스킹 표시, 위험 점수 갱신 및 종료 후 최종 결과 카드 표시를 사용자가 확인했다. 실제 탐지·마스킹 정확도는 별도 검증 대상이다.
- **확인한 내용:** 이번 조회·알림·종료 연결 테스트 4개와 기존 종료 호환성 테스트 1개, 총 5개 통과. 진행 중 분석 후 종료, 결과 보존, 알림 확인·만료, 마지막 번호 불일치, 저장 실패를 확인했다. 이전 분석 6개·STT 14개는 해당 단계 검증 기록이며 이번에 반복 실행하지 않았다.
- **다음 작업:** 배포 후보의 도메인·비용·Linux 모델 실행 환경을 확인하고 HTTPS/WSS 구성 예시를 실제 서버에서 검증한다. 토큰 발급·전달·폐기, 요청 제한의 배포 환경 조정과 기존 통화의 소유권 이전도 남았다. 이후 위험 통화 기록과 신고 자료 생성을 구현한다.
- **지연 측정:** 분석 API에 단계별 시간 로그·`Server-Timing` 헤더를 추가했다. 실제 샘플 1건의 서버 처리 6.444초 중 보정 3.490초, 문맥 판단 2.761초로 두 OpenAI 단계가 약 97%를 차지했다. 이 값은 통합 전 기준이다. 이후 단일 호출로 변경한 측정 결과는 아래에 기록했다. 모델·경고 정책은 유지했다.
- **현재 작업 브랜치:** `feature/server-v2.0-stt-relay`.
- 기존 AI 로더를 시작 과정에 연결했지만 기본 모드는 `disabled`다. 사용자 제공 임시 `checkpoints/risk_speech_v1.pt`는 기존 로더의 호환성 검사·CPU 로딩·샘플 추론을 통과했다. 이 파일을 사용한 HTTP 분석·OpenAI 호출·저장 결과 조회는 샘플 1건으로 확인했다. ElevenLabs·Android 연결과 탐지 성능은 아직 검증하지 않았다.

## 목표 파이프라인

아래는 구현할 목표 흐름이며, 현재 동작하는 기능 목록이 아니다.

```text
앱 마이크로 음성 수집
 → 새 서버: 음성을 ElevenLabs 실시간 STT에 중계
 → 새 서버: 중간·확정 인식 결과를 앱에 반환
 → 앱: 확정 문장의 개인정보를 기기에서 마스킹
 → 앱: 마스킹 성공 결과를 서버에 전송
 → 새 서버: 입력 확인 및 OpenAI 한 번 호출로 발화 보정·문맥 위험 판단
 → 새 서버: 보정 문장으로 기존 위험 탐지 AI 분석·누적 위험도 계산
 → 새 서버: 최종 경고·근거 구성, 결과 저장 및 앱 응답
 → 앱: 결과·경고 표시, 알림 수신확인
 → 마지막 발화 처리 완료 후 통화 종료·최종 결과 보존
```

음성 중계는 WebSocket으로, 마스킹된 확정 발화 분석은 HTTP API로 연결했다. STT 중간에는 처리 상태만 표시하고, 확정·마스킹된 문장만 화면 표시 및 분석 대상으로 삼는다. 메시지 형식은 [앱 계약 문서](document/APP_SERVER_CONTRACT.md)를 따른다.

**음성은 마스킹 전에 자체 서버와 ElevenLabs로 전달된다.** 기기 내에서 수행하는 것은 텍스트 마스킹이다. 음성·원문 텍스트의 보관·삭제 및 사용자 안내는 외부 음성 연결 전에 정한다. 시연 입력은 앱 마이크이며 실제 통화 음성 직접 수집을 전제로 하지 않는다.

## 구현 순서와 완료 기준

아래 단계 번호는 목표 흐름이다. 현재는 사용자 요청으로 STT 실연결·앱 작업을 보류하고 서버에서 독립적으로 구현할 수 있는 3단계를 먼저 연결했다. 보류한 단계는 완료한 것으로 처리하지 않는다.

| 단계 | 작업 | 완료 기준 | 현재 상태 |
|---|---|---|---|
| 0 | 최소 서버 | FastAPI 앱과 `/health` 응답 확인 | 완료 |
| 1 | ElevenLabs STT 중계 | 서버를 거쳐 음성을 보내고 중간·확정 텍스트 수신, 정상 종료·주요 연결 오류 처리 | 코드·대체 공급자 테스트 및 실제 인증/세션 시작·무음성 종료 확인, 실제 음성 인식 대기 |
| 2 | 앱 마이크·STT 연결 | 앱 음성을 서버에 보내고 인식 결과 표시, 중지 시 마지막 결과 수신 | 사용자 요청으로 보류 |
| 3 | 마스킹 계약·기존 분석 연결 | 토큰·발화 ID 규칙 통일, 마스킹 성공 결과를 보정·AI 계산·저장에 연결하고 앱에서 응답 수신 | 서버 연결·대체 객체 및 임시 모델의 실제 HTTP 샘플 확인 완료, 앱 확인 대기 |
| 4 | 학습 체크포인트 적용 | 학습 완료 `.pt` 호환성 확인 및 실제 모델로 서버 추론 성공 | 임시 `risk_speech_v1.pt` 인수·CPU 추론·HTTP 샘플 분석 확인, 학습 완료 여부·성능은 별도 확인 필요 |
| 5 | LLM 문맥 위험 판단 | 보정과 합친 단일 호출의 문맥 판단·근거를 기존 AI 결과와 함께 저장·응답 | AI 전 통합 호출·저장·응답 및 실제 API 2건 확인, 판단 품질·앱 안내 확인 대기 |
| 6 | 앱 결과·알림·통화 종료 | 결과 표시, 알림 조회·수신확인·중복 표시 방지, 남은 발화 처리 후 종료 연결 | 서버 조회·알림·일반 종료 연결/관련 검증 완료, 철회·삭제 및 앱 확인 대기 |
| 7 | 상시 배포·실기기 검증 | 외부 기기에서 전체 흐름·주요 실패 복구·응답 지연 확인 | 예정 |

- `.pt`를 기다리는 동안 1~3단계와 이후 연결 개발은 개발용 AI로 진행할 수 있다. 개발용 점수는 탐지 성능 검증에 사용하지 않는다. 4단계는 파일이 준비되는 시점에 조정할 수 있다.
- 5단계는 AI 실행 전에 현재 발화 보정과 세션 전체 문맥 판단을 한 번의 OpenAI 호출로 수행한다. AI 점수와 기존 경고 이벤트는 유지하고 `context_judgment`로 추가 안내·근거를 구분한다. LLM 판단으로 기존 경고를 해제하지 않는다. 통합 호출 실패 시 검증된 마스킹 입력으로 AI를 실행하고 보정 fallback·문맥 error를 구분한다. 상세 규칙은 [문맥 판단 계약](document/CONTEXT_RISK_CONTRACT.md)을 따른다.
- 배포 후보는 AWS Lightsail 2(임시)다. 최종 사양과 실제 배포는 아직 확정·검증되지 않았다.

## 기능 명세 적용 방침

[기능 명세서](<../PIC 프로젝트_기능명세서_2026-10-28.md>)의 요구사항을 단계별로 연결한다. 아래 내용은 구현 방침이며 현재 구현 완료를 뜻하지 않는다.

- **일반 종료:** 마이크·새 음성 전송은 즉시 중단한다. 이미 전송된 음성의 마지막 확정 결과와 처리 중인 마스킹·분석까지 반영한 뒤 종료를 확정한다. 실패 시 마지막 성공 결과와 미완료 상태를 구분한다.
- **STT 표시:** 중간에는 처리 상태만 표시하고 확정·마스킹된 문장을 표시한다. 원문은 표시·저장하지 않는다.
- **보정 실패:** 검증된 마스킹 입력으로 분석을 계속하고 보정 실패·대체 입력 사용 상태를 기록·반환한다. 마스킹 실패·입력 계약 위반은 허용하지 않는다. 기존 backend의 502 중단 동작과 다르므로 3단계에서 조정한다.
- **마스킹 계약:** `[PERSON]`, `[PHONE_NUMBER]`, `[RRN]`, `[ACCOUNT_NUMBER]`, `[ADDRESS]`, `[OTP]`, `[CARD_NUMBER]`, `[BIRTH]`, `[EMAIL]`, `[PW]`, `[MASKED]` 토큰을 허용한다.
- **동의 철회:** 앱은 즉시 수집·전송 중단 및 로컬 기록 삭제. 서버는 요청 수신 후 해당 세션의 추가 처리·저장을 차단하고 발화·분석·경고·알림 기록을 삭제한 뒤 완료 응답한다. 진행 중 작업의 늦은 결과는 폐기한다. 앱은 삭제 대상 세션 ID를 유지하고 실패 시 재시도하며 완료 응답 전에는 삭제 대기로 표시한다. 최소 철회 상태는 분석 내용과 분리해 세션 재생성을 막는다.
- **단계 반영:** 1~2단계에 10분 세션 제한·동의 후 입력·원문 미저장, 3단계에 보정 실패 처리·토큰 계약, 6단계에 종료 마무리·철회 및 삭제를 연결한다. 자체 서버의 삭제와 외부 서비스의 보관 정책은 구분한다.
- **문서 역할:** 새 서버 계약과 진행 상황은 이 문서에서 관리하고 세부 계약은 연결 단계에서 확정한다. 기존 backend 문서는 재사용 참고 자료다.

## 기존 코드 재사용

기존 `backend`는 전환이 끝날 때까지 보존한다. 필요한 기능을 단계별로 가져오며, 복사만으로 연결 완료 처리하지 않는다.

- 각 단계에서 새 코드를 작성하기 전에 해당 기능의 기존 구현과 API 계약을 확인하고, 현재 파이프라인에 맞는 코드를 우선 재사용한다. 새 서버를 만든다는 이유로 보정·계산·저장 등 이미 구현된 기능을 처음부터 다시 작성하지 않는다.
- 그대로 사용할 수 있는 모듈은 직접 호출하고, 입출력이 다르면 필요한 변환만 추가한다. 기존 서버에 강하게 묶인 부분은 해당 단계에 필요한 범위만 이식한다. 같은 로직을 복사해 두 곳에서 별도로 유지하거나 불필요한 호환 계층을 만들지 않는다.
- 작업 설명에 재사용할 파일·함수와 새로 구현할 부분을 구분한다. 연결 후에는 이 문서에 실제 재사용한 경로와 확인한 흐름을 기록한다.

**현재 재사용 상태:** `backend.lifespan.lifespan`, `pipeline_service.analyze_utterance()`·`retry_utterance_analysis()`와 이 함수가 호출하는 보정·문맥·계산·경고·저장 코드를 직접 연결했다. 5단계에서는 기존 `analysis_service`의 저장 직전 선택적 `context_judge` 호출로 문맥 결과를 같은 기록에 저장한다. 6단계에서는 `get_analysis_result()`·`end_conversation()`과 `NotificationService.list_pending()`·`acknowledge()`를 공개했다. 파일 저장·잠금·계산을 새로 구현하지 않았다. 기본 AI 모드는 disabled이며 임시 체크포인트는 아래 설정으로 활성화한다.

| 기존 자산 | 새 서버에서 사용할 시점 |
|---|---|
| `models/llm_correction`, `models/context_manager` | 3단계 보정·문맥 구성 |
| `risk_speech_ai`, 기존 AI 어댑터·로더·누적 계산 | 3~4단계 AI 연결 |
| 기존 통화 저장·조회·순서 관리·실패 재시도 | 3단계 분석 연결부터 필요한 범위 이식 |
| `models/warning_manager`, 기존 경고 연동 | 3단계 기존 경고 연결, 5단계 새 판단 정책 반영 |
| 기존 알림 조회·수신확인·통화 종료 | 6단계 앱 연결 |

기존 테스트 통과 기록은 기존 기능의 검증 근거다. 새 서버의 STT·앱·LLM 통합 검증 완료를 의미하지 않는다.

## STT 구현과 앱 계약

상세 입력·출력 JSON, 음성 형식, 앱 처리 순서, 오류·종료 규칙은 [APP_SERVER_CONTRACT.md](document/APP_SERVER_CONTRACT.md)를 기준으로 한다. 코드 변경 시 이 계약도 함께 갱신한다.

| 파일 / 함수 | 역할 |
|---|---|
| `config.py` / `load_stt_settings()` | 서버 환경변수에서 키 읽기, STT 설정 |
| `stt/contracts.py` / `parse_client_message()`, `validate_audio_chunk()` | 앱 제어 메시지·음성 길이 검증 |
| `stt/elevenlabs.py` / `open_stt_connection()`, `send_audio()`, `receive_event()` | 공급자 연결·변환·응답 검증 |
| `stt/router.py` / `stt_websocket()`, `relay_audio()` | 앱 경로·음성/텍스트 중계·발화 번호·종료·시간 제한 |
| `main.py` | STT 라우터 등록, `/health` 유지 |

- `ELEVENLABS_API_KEY`는 실행 프로세스의 환경변수에서 읽는다. 새 서버는 프로젝트 루트 `.env`를 자동 로딩한다. `server/.env.example`은 복사용 안내 파일이다. `/health`는 키 없이도 동작한다.
- `scribe_v2_realtime`, 한국어 `ko`, 16kHz 모노 16비트 PCM을 사용한다.

### 보정·문맥 판단 통합 연결

```text
마스킹 입력 검증 → OpenAI 한 번 호출(현재 문장 보정 + 전체 문맥 판단)
```

- `analysis/context_service.py::prepare_utterance()`가 통합 입력·Responses API 호출을 담당한다. `context_contracts.py::parse_prepared_utterance()`가 형식·근거 ID와 기존 `validate_masking_token_preservation()`을 이용한 토큰 검증을 수행한다.

- `analysis_service._process_model_result_locked()`는 사전 문맥 판단을 기존 응답에 합쳐 저장한다. 공유 `ContextJudgmentResult`와 응답 JSON·저장 스키마는 유지한다.
- 통합 호출 실패는 보정 `fallback`·문맥 `error`, 모델 미설정은 보정 `fallback`·문맥 `not_run`이다. 이때 검증된 마스킹 입력으로 AI를 실행한다. AI만 실패해도 먼저 성공한 문맥 판단은 보존한다.
- `retry_utterance_analysis()`·`_retry_model_result_locked()`는 같은 발화의 문장·보정 상태·문맥 판단을 재사용한다. 새 서버의 AI 재시도는 OpenAI를 재호출하지 않는다. 통합 LLM만 재시도하는 API는 없다.

### Android 분석 결과 복구 (2026-11-06)

사용자가 실기기에서 최종 결과 카드 표시를 확인했다. Android에서 분석 응답 실패 시 음성 수집을 중단하고, 사용자의 재확인으로 기존 결과 조회 API와 AI 재시도 API를 이용해 해당 발화를 복구한다. 조회가 404면 동일 마스킹 발화를 재전송하고 중복 409면 다시 조회한다. 복구 전 다음 발화와 종료는 기다린다. 관련 Android 단위 테스트와 debug 빌드에 성공했으며, 실제 통신 실패를 통한 실기기 확인은 남았다. 앱 종료 후 복구 상태 보존은 지원하지 않는다.

### 서버 철회·삭제 기초 (2026-11-06)

`POST /api/v1/conversations/withdraw`는 통화 ID의 철회 표시를 분석 기록과 분리해 저장하고, 기존 통화 잠금으로 진행 중인 작업이 끝난 뒤 통화 파일을 삭제한다. 철회 표시 후에는 새 조회·저장과 늦은 저장을 거부하며 반복 철회도 성공한다. 단일 서버 프로세스 기준이며 외부 API 제공자의 데이터 삭제는 포함하지 않는다. 서버 철회 및 기존 저장 관련 테스트 9개가 통과했다.

앱은 철회 시 수집을 중단하지만 아직 서버 API를 호출하거나 과거 세션 ID를 보관하지 않는다. 디버그 미리보기 타이머가 실제 서버 삭제 없이 완료를 표시하던 동작을 차단해 삭제 대기로 표시하도록 고쳤다. Android 단위 테스트와 빌드는 성공했으나 기기 연결이 없어 설치·실기기 확인은 못 했다. 인증·세션 소유권 검증이 없으므로 외부 공개 전 이를 추가해야 한다.

### Android 철회·삭제 연결 (2026-11-06)

앱은 분석 요청 전에 기존 동의 DataStore에 서버 주소와 세션 ID를 등록한다. 철회 시 수집·전송을 중단하고 동의 철회를 저장한 뒤 각 세션에 서버 삭제 API를 호출한다. 서버에서 완료를 확인한 세션만 목록에서 제거하며, 실패한 세션은 앱 재실행 후에도 삭제 대기로 남고 사용자가 재시도할 수 있다. 동의 철회와 세션 등록은 같은 DataStore에서 처리한다. 앱의 단위 테스트 36개와 debug 빌드 통과, 실제 기기·서버 확인은 남았다.

이 변경 전 앱에서 생성한 세션은 ID를 추적하지 않았으므로 자동 삭제 대상에 포함할 수 없다. 자체 서버 삭제가 외부 API 제공자의 데이터 삭제를 뜻하지 않으며 서버는 단일 프로세스·인증 미구현 상태다.

### 기기 인증 저장 기반 (2026-11-07)

로그인 없이 기기별로 통화 기록을 구분하는 방향을 선택했다. `server/security/device_store.py`는 무작위 기기 토큰 발급, 토큰 해시 저장·확인, 통화와 기기 연결 및 소유권 확인 기능을 제공한다. 기존 통화 분석·저장 코드는 재사용하며 별도 인증 저장 기반만 추가했다. 기기별 통화 접근과 재시작 후 보존, 잘못된 저장 파일 거부의 단위 테스트 2개가 통과했다.

이 코드는 아직 HTTP·WebSocket이나 Android와 연결되지 않았다. 따라서 현재 서버는 여전히 인증 없이 접근 가능하며 외부 공개에 적합하지 않다. 등록 요청 남용 방지, 인증 정보 보관·분실, 기존 통화 처리, TLS 및 단일 worker 조건도 API 통합 단계에서 해결해야 한다. 시연용 토큰만으로 앱의 정품 여부를 증명하지는 않는다.

### 서버 기기 인증·통화 소유권 연결 (2026-11-07)

STT WebSocket과 분석·재시도·조회·종료·철회·알림 API는 `Authorization: Bearer <기기 토큰>`을 요구한다. 서버가 STT 세션을 만들 때 기기와 통화를 연결하고, 각 통화 요청에서 소유권을 확인한다. 인증 실패는 HTTP 401, 다른 기기 또는 등록되지 않은 통화는 404다. WebSocket은 연결 수락 전에 인증을 검사한다. 소유권 검사는 기존 분석·저장·철회 함수를 그대로 호출하기 전 수행한다.

운영자용 `python -m server.security.provision_device`는 토큰을 발급하며 공개 등록 API는 만들지 않았다. 저장소 잠금은 프로세스 내부에서만 동작하므로 **서버를 중지한 뒤에만 발급 명령을 실행**해야 한다. 토큰을 출력·공유·기록할 때 취급에 주의한다. 서버는 토큰 원본 대신 해시를 저장한다. 관련 테스트 28개 통과. 기존 기능 전용 테스트는 인증을 대체하고, 별도 인증 테스트에서 무인증·다른 기기 차단 및 WebSocket 소유권 등록을 확인했다.

아직 Android는 토큰을 보관하거나 전송하지 않는다. 새 서버 코드 재시작 시 기존 앱과 토큰 없이 호출하는 수동 텍스트 테스트가 거절된다. 기존 통화에는 소유권 정보가 없어 접근할 수 없으며, 기존 기록 이전·철회 재시도 방식은 Android 연동 전 별도 처리해야 한다. 현재 실행 중인 구버전 서버 프로세스는 재시작 전까지 보호되지 않는다. TLS, 기기 토큰 안전 전달·보관·폐기, 남용 제한, 단일 worker 유지 및 실기기 검증 전에는 외부에 공개하지 않는다.

### Android 기기 인증 연결 (2026-11-07)

별도 Android 작업 트리의 `DeviceTokenStore`가 운영자가 발급한 기기 토큰을 Android Keystore의 AES-GCM 키로 암호화해 보관한다. 토큰은 등록된 서버의 scheme·호스트·포트에만 전달한다. 비암호화 주소는 debug 빌드의 로컬 개발 주소에만 허용하며 리다이렉트는 따라가지 않는다. 앱은 WebSocket과 발화 분석·재시도·조회·종료·철회 요청에 인증 헤더를 추가한다. 앱의 기존 `RiskAnalysisClient`와 `SttSession`을 재사용한다.

화면에는 수동 토큰 등록을 추가했다. 삭제 대상 통화가 남아 있으면 기존 토큰을 다른 토큰으로 바꾸지 않는다. Android 단위 테스트 38개와 debug 빌드가 통과했고 테스트의 HTTP·WebSocket 헤더는 대체 서버에서 확인했다. 휴대폰 연결이 없어 실제 Keystore와 실기기 종단 동작은 확인하지 못했다. 기존 인증 이전 통화의 소유권 이전·삭제, 토큰 분실·복구·폐기, 제한 없는 인증 시도 및 HTTPS/WSS 배포는 아직 해결되지 않았다.

### 기기 인증 실기기 확인 (2026-11-07)

사용자가 발급된 기기 토큰을 앱에 등록하고 USB 연결로 서버에 접속해 위험 점수와 종료 후 최종 결과가 표시되는 것을 확인했다. 서버의 인증 없는 결과 조회는 401을 반환했다. 최근 분석 파일이 종료 상태이며 등록된 기기와 연결된 것도 확인했다. 타 기기 토큰의 접근 거부는 기존 서버 단위 테스트에서 확인했으며 실기기에서는 아직 확인하지 않았다. 실제 운영을 위한 TLS·발급 및 토큰 관리·남용 제한은 남아 있다.

### 요청 남용 제한 (2026-11-07)

`server/security/limits.py`의 단일 프로세스 메모리 제한을 기존 인증·분석·STT 경로에 연결했다. 임시 시연 기본값은 기기별 분석·재시도 합계 60초당 30회, 동시 STT 연결 기기당 2개·서버 전체 20개다. 인증 실패가 같은 접속 주소에서 60초 내 30회 누적되면 일시 차단한다. 분석·인증 제한 초과 HTTP 요청은 429를 반환한다. 동시 STT 제한은 WebSocket 연결 수락 전 거부하고 연결 종료 시 자리를 반환한다. 기존 음성 10분 제한과 분석·저장 코드는 유지한다. 관련 테스트 28개 통과; 실제 배포 부하·실기기 제한 동작은 미검증이다.

제한 값은 검증된 운영 수치가 아니라 시연용 초기값이다. 메모리 기반이므로 재시작 시 초기화되며 여러 worker나 서버에 걸쳐 공유되지 않는다. 인증 실패 제한은 직접 접속 주소를 기준으로 하므로 프록시 배포 때 신뢰할 프록시·실제 주소 처리를 정하고 같은 네트워크 사용자 간 영향도 확인해야 한다. 이 기능만으로 분산 공격을 막거나 비용 상한을 보장할 수 없다. 결과 조회·통화 종료·철회 요청은 분석 횟수 제한 대상이 아니다.

### HTTPS/WSS 배포 구성 준비 (2026-11-07)

`server/deploy/`에 Caddy 리버스 프록시와 단일 worker FastAPI systemd 실행 예시, 설치·검증 절차를 작성했다. 기존 API·인증·저장을 재사용하며 실행 중인 로컬 서버는 바꾸지 않았다. Caddy는 HTTPS/WSS를 처리하고 FastAPI는 로컬 주소에만 바인딩하는 구성이다. 앱의 서버 출처별 토큰과 기존 삭제 대상 기록은 배포 주소 전환 전에 별도 확인해야 한다. 이 단계에서는 설정 파일만 준비했으며 AWS 자원 생성, Linux 설치, Caddy 설정 검증, 인증서 발급과 실기기 HTTPS/WSS 연결은 아직 수행하지 않았다.

### 배포 사양 사전 조사 (2026-11-07)

임시 체크포인트 크기는 약 1.35GB이며, 실행 중인 Windows `server.main:app` 프로세스의 현재/최대 작업 집합은 약 887/2,187MiB였다. 단일 프로세스의 관측값이므로 Linux 배포 용량의 보증은 아니다. AWS 서울 리전의 Linux 일반형 4GB를 시연용 검토 후보로 두고 실제 Linux 기동과 사용량을 측정하기로 했다. AWS 계정과 도메인은 아직 없으며 실제 자원 생성과 과금은 시작하지 않았다. 사양·가격 근거와 제약은 `server/deploy/README.md`에 기록했다.
